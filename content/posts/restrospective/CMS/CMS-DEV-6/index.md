# 코드 리뷰에서 나온 지적, 지금 고칠까 이슈로 남길까

# 배경

출결 코드 발급 로직(`ensureAttendanceRowsExist` — 코드 발급 시 대상자 중 `Attendance` 로우가 없는 사람만 골라 `NOT_CHECKED` 상태로 생성하는 메서드) PR에 CodeRabbit이 동시성 경쟁 조건 가능성을 지적했다. 관리자 두 명이 정확히 같은 순간에 같은 일정의 코드를 재발급하면, 각자 "없으니 생성해야지"라고 판단해서 중복 생성이나 정합성 문제가 생길 수 있다는 내용이었다.

## 고민

지적 자체는 타당했다. 하지만 이 PR 안에서 바로 락(비관적 락, unique 제약 등)을 걸어서 고칠지, 아니면 별도로 남겨둘지 판단이 필요했다.

판단 기준으로 삼은 두 가지.

- **발생 가능성**: 지금 팀/서비스 규모에서 관리자 두 명이 정확히 같은 순간에 같은 일정의 코드를 재발급할 확률이 실제로 얼마나 되는가
- **영향 범위**: 실제로 터졌을 때 데이터가 깨지는가, 아니면 단순 중복 요청 정도로 끝나는가

이번 경우엔 관리자 수 자체가 적고, 코드 재발급이라는 액션도 자주 발생하지 않는 데다, 최악의 경우에도 중복 로우 생성 정도로 그칠 가능성이 높다고 판단했다.

## 결정

이번 PR에서 바로 고치지 않고 **별도 GitHub 이슈로 분리**해서 남겨뒀다. PR 자체는 기능 요구사항을 충족한 상태로 먼저 머지하고, 동시성 방어는 우선순위를 정해서 다음에 처리하기로 했다.

## 참고

모든 리뷰 코멘트를 하나의 PR 안에서 다 해결하려 하면 PR이 계속 커지고, 리뷰어도 원래 보려던 변경사항과 부가적인 리팩터링을 같이 봐야 해서 리뷰 품질이 떨어질 수 있다. "지금 고칠 것"과 "이슈로 남길 것"을 구분하는 기준이 팀에 없다면, 위 두 가지(발생 가능성 × 영향 범위) 정도를 짧게 합의해두는 것도 방법이다.

## 한 줄 교훈

리뷰에서 나온 모든 지적을 그 자리에서 다 고치는 게 항상 정답은 아니다. 발생 가능성과 영향 범위를 근거로 우선순위를 매기고, 필요하면 이슈로 분리하는 것도 정상적인 프로세스다.
