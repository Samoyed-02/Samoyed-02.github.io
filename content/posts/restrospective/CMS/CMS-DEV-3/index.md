# "조회 API를 추가하자"가 항상 답은 아니다 — Redis 저장 방식 문제

# 배경

관리자가 발급한 6자리 출결 코드를 Redis에 저장하는 기능을 만들었다. 처음 설계는 코드를 **해시**로 저장하는 것이었다. 그런데 이후 두 가지 문제가 나왔다.

- 관리자가 페이지를 새로고침하면 방금 발급한 코드가 화면에서 사라진다
- 다른 관리자가 같은 화면에 접속하면 이미 발급된 코드를 볼 방법이 없다

이 문제에 대한 팀의 첫 제안은 "그럼 조회용 GET 엔드포인트를 추가하면 되지 않냐"는 것이었다.

## 왜 이 제안이 문제를 안 풀었나

GET 엔드포인트는 **Redis에 있는 값을 그대로 꺼내서 돌려주는 통로**일 뿐이다. 값 자체를 만들어내지 않는다.

```
GET 엔드포인트가 하는 일:
  Redis에서 key로 값을 조회 → 그 값을 그대로 응답
```

이 시점 Redis 안에는 이런 값이 들어있었다.

```
attendance-code:87 = "a3f9c2e8b1d4..." (해시값)
```

GET을 아무리 잘 만들어도 돌려줄 수 있는 값은 이 해시값뿐이다. 관리자 화면에 `a3f9c2e8b1d4...`가 뜬다고 해서 사용자에게 "이 코드로 체크인하세요"라고 안내할 수 없다 — 사용자는 원래 6자리 숫자(`483920`)를 입력해야 하기 때문이다.

**문제는 "GET이 없다"가 아니라 "GET이 있어도 보여줄 게 없다"였다.** 엔드포인트(통로)와 저장 방식(데이터)이 별개 문제라는 걸 놓친 것이다.

## 해결

순서를 바로잡았다.

1. Redis 저장 방식을 해시 → **평문**으로 변경
2. 그 다음 조회용 GET 엔드포인트 추가

```
attendance-code:{scheduleId} = "483920"   (TTL 300초, 재발급 시 덮어쓰기)
```

## 평문 저장이 괜찮은 이유

무조건 해시가 "더 안전한 선택"은 아니다. 이 코드는 애초에 관리자가 화면에 띄워서 여러 사람에게 공개하는 값이고, TTL이 5분으로 짧아서 유출돼도 피해 범위가 제한적이다. 오히려 해시로 저장하면 정작 필요한 "재조회해서 다시 보여주기" 기능 자체가 불가능해진다. 보안 원칙을 기계적으로 적용하기보다 실제 사용 맥락에 맞춰 판단해야 하는 사례였다.

## 한 줄 교훈

"조회 기능이 없어서 문제"라는 진단이 나오면, 그 전에 "조회했을 때 돌려줄 데이터가 애초에 올바른 형태로 저장되어 있는가"부터 확인해야 한다.
