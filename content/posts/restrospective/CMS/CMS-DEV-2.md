## 들어가며

이슈 #11 `관리자 출결 조회 및 코드 관리 API 구현`을 진행했다. 앞선 #10(관리자 일정)이 "기획 문서 재확인" 이야기였다면, 이번엔 성격이 다르다. **Redis 저장 방식 하나를 잘못 잡았다가 설계 자체를 갈아엎은 이야기**, 그리고 실제 구현 이후 **여러 브랜치가 같은 파일을 동시에 건드리면서 생긴 Git 트러블슈팅**이 이번 글의 핵심이다.

## 무엇을 만들었나

`Attendance` 엔티티와 Redis를 대상으로 관리자용 엔드포인트 4개를 구현했다.

- `GET /admin/attendances` — 일정+파트별 출결 현황 조회
- `PATCH /admin/attendances/{attendanceId}` — 출결 상태 수정
- `POST /admin/schedules/{scheduleId}/attendance-code` — 출결 코드 생성/재발급
- `GET /admin/schedules/{scheduleId}/attendance-code` — 현재 출결 코드 조회

본인 체크인(`POST /schedules/{scheduleId}/attendance-check-ins`)은 다른 팀원 담당 범위라 처음부터 이슈 범위에서 제외해뒀다.

## 문제 1 — "GET을 추가하자"는 제안이 사실은 문제를 안 풀었다

출결 코드 설계 초반엔 Redis에 6자리 코드를 **해시로** 저장하기로 했었다. 그런데 이후 "관리자가 새로고침하면 코드가 사라진다", "다른 관리자가 접속했을 때 방금 생성된 코드를 볼 수 없다"는 문제가 나왔고, 팀에서는 "그럼 조회용 GET 엔드포인트를 추가하면 되지 않냐"는 제안이 나왔다.

언뜻 맞는 말처럼 들렸지만, 한 단계를 건너뛴 제안이었다. GET 엔드포인트는 **Redis에 있는 값을 그대로 꺼내서 돌려주는 통로**일 뿐이다. Redis 안에 애초에 해시값만 들어있다면, GET을 아무리 잘 만들어도 그 해시값을 돌려줄 수밖에 없다. 사용자는 원래 6자리 숫자(`483920`)를 입력해야 하는데, 관리자 화면엔 복원 불가능한 해시값만 뜨는 상황이 되는 것이다.

즉 순서가 틀렸었다.

1. Redis 저장 방식을 해시 → **평문**으로 바꾸는 게 먼저
2. 그 다음에 GET 엔드포인트를 추가하는 게 그 다음

이 순서를 팀에 짚어준 뒤, "평문 저장 + GET 추가" 방향으로 최종 확정했다. 최종 설계는 이렇게 정리됐다.

- **키**: `attendance-code:{scheduleId}`
- **값**: 6자리 코드 **원문**
- **TTL**: 고정 5분
- 재발급 시 새 코드로 덮어쓰기, 관리자 여러 명이 동시에 접속해도 동일한 값을 GET으로 재조회 가능

평문 저장이 보안상 걱정될 수 있지만, TTL이 5분으로 짧아서 유출 시 피해 범위가 제한적이라는 점, 그리고 애초에 "관리자가 화면에 띄워서 여러 사람에게 공개하는 값"이라는 코드의 성격상 평문 저장이 오히려 기능 요구사항에 맞는 선택이었다.

## 문제 2 — `MissingServletRequestParameterException`이 500으로 떨어지고 있었다

`GET /admin/attendances`는 `scheduleId`를 필수 쿼리 파라미터로 받는데, 이 파라미터를 빼고 테스트하니 400이 아니라 500이 떨어졌다. 원인을 보니 `GlobalExceptionHandler`에 `MissingServletRequestParameterException`을 처리하는 핸들러가 아예 없었다. 스프링이 필수 파라미터 누락을 감지해서 던지는 예외인데, 이걸 잡아주는 핸들러가 없으니 예상치 못한 예외로 취급되어 500으로 떨어진 것이다. 이 부분은 이번 기능 구현 중 발견한 기존 코드의 결함이라, 핸들러를 추가하고 별도로 커밋했다.

## 문제 3 — 브랜치 3개가 같은 파일을 동시에 건드리고 있었다

`feat/11`은 아직 develop에 머지되지 않은 `feat/10` 위에 쌓아올린 브랜치였다. 이 상태에서 `AppUserRepository`를 건드려야 했는데, 알고 보니 같은 시점에 **세 개의 브랜치가 이 파일을 동시에 수정 중**이었다.

- `feat/11`(본인): cohort+역할+계정상태로 대상자를 찾는 파생 쿼리 메서드 추가
- Lions 기능 브랜치: `@Query`로 `findLions` 메서드 추가
- 회원 관리 브랜치: `JpaSpecificationExecutor<AppUser>` 상속 추가

develop 머지 시점에 세 변경사항이 전부 충돌했고, 어느 한쪽을 버리는 게 아니라 **세 메서드/상속 전부를 살리는 방향으로 수동 병합**해야 했다. 여기에 더해 `docker-compose.yml`도 충돌이 났는데, 내가 Redis 서비스를 새로 추가해뒀던 게 이미 develop에 먼저 반영되어 있어서 develop 쪽 버전을 그대로 채택하는 걸로 정리했다.

이 경험으로 확실히 배운 건, **공용 파일(Repository, docker-compose 같은)을 건드리기 전에는 최소한 "지금 이 파일을 누가 같이 건드리고 있는지" 정도는 확인하고 시작해야 한다**는 것이다. 브랜치를 스택으로 쌓아올리는 전략 자체는 develop이 불안정한 시기엔 유효했지만, 공용 파일 충돌 위험까지는 줄여주지 못했다.

## 문제 4 — 로컬 테스트가 카카오 OIDC 로그인 의존성 때문에 막혔다

기능 구현을 마치고 Postman으로 실제 요청을 테스트하려 했는데, 인증 자체가 안 됐다. `JwtTokenProvider.createToken()`으로 직접 서명한 토큰은 401로 거부됐다 — 필터가 실제 세션 컨텍스트 기준으로 검증하도록 설계되어 있어서, 자체 발급 토큰으로는 우회가 안 되는 구조였다.

처음엔 `JwtAuthenticationFilter`가 `Long userId`를 principal로 잘못 세팅하는 버그인가 의심했는데, 인증 담당 팀원에게 확인해보니 develop에는 이미 수정된 상태였다. 진짜 원인은 로컬 환경에 카카오 로그인용 자격 증명(`KAKAO_CLIENT_ID`, `KAKAO_CLIENT_SECRET`, `KAKAO_REDIRECT_URI`)이 없었던 것 — 게다가 설정된 `KAKAO_REDIRECT_URI`가 운영 서버 주소로 되어 있어서, 로컬 테스트를 하려면 카카오 개발자 콘솔에 `http://localhost:8080/api/auth/kakao/callback`을 별도로 등록해야 하는 상황이었다.

결국 이번 PR에서는 Postman 테스트를 "카카오 인증 인프라 제약으로 보류"라고 명시하고 제출했다. 참고로 테스트 토큰을 뽑기 위해 임시로 `TokenGeneratorTest` 파일을 만들어 썼는데, 어차피 401로 막혀서 목적을 달성하진 못했고 이후 삭제했다.

## 리뷰에서 나온 이슈 하나는 의도적으로 미뤘다

CodeRabbit 리뷰에서 `ensureAttendanceRowsExist`(코드 발급 시 대상자의 `Attendance` 로우를 없으면 생성하는 로직)에 동시성 경쟁 조건이 있을 수 있다는 지적이 나왔다. 관리자 두 명이 동시에 코드를 재발급하면 레이스 컨디션이 발생할 여지가 있다는 것이었는데, 현재 팀 규모에서 관리자 두 명이 정확히 같은 순간에 같은 일정의 코드를 재발급할 가능성은 낮다고 판단해서 이번 PR에서 바로 고치지 않고 **별도 GitHub 이슈로 남겨두는 쪽**을 택했다. 모든 지적을 그 자리에서 다 고치기보다, 발생 가능성과 영향 범위를 따져서 우선순위를 매기는 것도 필요하다고 느꼈다.

## 배운 점

1. **"조회 기능을 추가하자"는 제안이 항상 문제를 푸는 건 아니다.** 통로(엔드포인트)와 데이터(저장 방식)를 분리해서 생각해야, "왜 이 GET은 쓸모가 없지?" 하는 상황을 피할 수 있다.
2. **여러 브랜치가 겹칠 만한 공용 파일은 건드리기 전에 미리 확인하는 게 머지 후 삽질보다 훨씬 싸다.** `AppUserRepository`처럼 여러 기능이 공유하는 파일은 세 갈래 충돌까지 갈 수 있다는 걸 이번에 체감했다.
3. **로컬 개발 환경이 실제 운영 인증 흐름(OAuth 등)에 강하게 의존하면, 기능 구현이 끝나도 테스트가 막힐 수 있다.** 이런 제약은 미리 알았다면 팀 차원에서 로컬용 카카오 앱을 별도로 등록해두는 식으로 대비할 수 있었을 것 같다.
4. **리뷰에서 나온 모든 지적을 그 PR 안에서 다 해결할 필요는 없다.** 영향 범위와 발생 가능성을 근거로 "지금 고칠 것 vs 이슈로 남길 것"을 구분하는 게 오히려 리뷰 프로세스를 건강하게 만든다.

#10과 #11을 거치며 느낀 공통점은, 문서(기획/정책)든 인프라(Redis/Git)든 **"확정됐다", "이미 되어있다"고 가정한 부분을 다시 열어봤을 때 실제로는 다른 경우가 많았다**는 것이다. 다음 기능부터는 구현 시작 전에 관련 문서와 공용 파일 현황을 한 번 더 훑어보는 걸 습관으로 만들어야겠다.
