개요 📃

수원대학교 멋쟁이사자처럼(LikeLion) 동아리 운영을 위한 통합 관리 시스템(CMS)을 개발한다. 회원 가입·승인, 프로젝트 아카이빙, 세션 자료실, 공지, 일정, 출결, 활동증명서 발급까지 동아리 운영 전 과정을 하나의 백엔드에서 처리하며, 관리자와 일반 회원의 권한을 분리해 접근을 제어한다. API 45개 엔드포인트, 11개 도메인 엔티티 규모의 백엔드를 단독으로 설계·구현했으며, 현재는 Kotlin으로 마이그레이션을 진행 중이다.

역할 🙋🏻‍♂️

✦ Backend 담당 — API 설계부터 구현까지 전 도메인 단독 수행, ERD·엔티티·인덱스 설계, 응답 컨벤션 수립 및 문서화

Skills 🛠️

✦ Java, Spring Boot, Spring Data JPA

✦ MySQL, Redis

✦ Kakao OAuth2, JWT

✦ AWS S3 (Presigned URL 업로드/다운로드)

✦ OpenAPI 3.1 기반 API 명세

백엔드 개발 & 트러블슈팅 🔒

응답 객체 생성 방식 통일

AS-IS

같은 응답 객체를 팀원 두 명이 서로 다른 스타일로 각자 작성해, 병합 시점에 충돌과 빌드 실패가 발생했습니다.

TO-BE

원인을 분석해 응답 객체는 생성자를 직접 노출하지 않고 정적 팩토리 메서드로만 생성하는 구조로 통일하고, 컨벤션 문서로 정리해 재발을 구조적으로 차단했습니다.

원인 불명 예외 해결

AS-IS

데이터베이스에서 가져오는 숫자 값이 비어 있을 수 있는데도 응답 객체에서는 항상 값이 있다고 가정하는 타입으로 받아, 값이 비면 어떤 항목이 문제인지 알 수 없는 예외로만 나타나 원인 추적이 어려웠습니다.

TO-BE

데이터베이스에서 가져오는 값은 비어 있을 수 있음을 표현하는 타입으로 통일하고, 서버가 직접 계산해 항상 값이 채워지는 항목에만 예외적으로 기존 방식을 허용하는 규칙으로 정리해 원인 추적이 가능한 구조로 개선했습니다.

시간대 불일치 리스크 사전 차단

AS-IS

운영 서버에 시간대가 별도 설정되어 있지 않으면 시스템 기본 시간대가 세계 표준시로 동작해, 저장되는 시각 값이 한국 시간과 9시간 어긋날 수 있는 잠재 리스크가 있었습니다.

TO-BE

저장 시각은 시간대 정보 없는 값으로, 다운로드 링크 만료처럼 특정 순간을 가리키는 값만 시간대 정보를 포함한 값으로 쓰도록 설계 문서화 단계에서 기준을 분리해 운영 전에 혼선을 예방했습니다.

불필요한 공통 응답 구조 제거

AS-IS

성공 응답을 공통 래퍼로 한 번 더 감싸던 기존 관행이 있었으나, 실제로는 어디서도 소비되지 않고 있었습니다.

TO-BE

성공 응답은 결과 데이터를 그대로 반환하고 상태 코드는 응답 객체로 표현하며, 에러만 공통 예외 처리기가 표준 에러 포맷으로 감싸는 원칙으로 응답 구조를 단순화했습니다.
